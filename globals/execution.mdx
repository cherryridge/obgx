# Execution

## General

This page defines behavior that occurs when OBGX operations are performed. It does not prescribe a host language, runtime, or error-handling mechanism.

The types on which operations act are defined by the [Type System](type).

## Namespaces

A host must associate exactly one [namespace](terminology#namespace) with each pack. A host must associate the same namespace with all OBGX operations that it considers to originate from the same pack. Multiple packs may be associated with the same namespace.

An OBGX operation must not change the namespace associated with its caller pack.

When a pack registers a game object through an OBGX interface, the host must register the game object under the namespace associated with the caller pack and the provided [`id`](type#id).

An operation that registers a game object or modifies an existing game object's registration must identify that game object with an `id` and must use the namespace associated with the caller pack.

An operation that can only target a game object under the namespace associated with the caller pack must identify that game object with an `id`. An operation that may target a game object under another namespace must identify that game object with a [`refid`](type#reference-id).

OBGX do not specify how a host handles multiple registrations with the same namespace and `id`.

OBGX does not specify how a host determines, stores, or internally represents the association between a pack and its namespace, including how the host determines whether operations originate from the same pack.

## Numeric Operations

### Integer Arithmetic

When the result of signed integer arithmetic exceeds the maximum value of its type, it wraps through the minimum value. When it falls below the minimum value, it wraps through the maximum value.

When the result of unsigned integer arithmetic exceeds the maximum value of its type, it wraps through zero. When it falls below zero, it wraps through the maximum value.

### Floating-Point Arithmetic

Floating-point arithmetic must follow the IEEE 754 standard for binary floating-point arithmetic, **when observed from an OBGX interface**. This includes the definition of special values such as `NaN` and infinities, as well as rounding, overflow, and underflow behavior.

## Faults

A fault occurs when a required execution precondition of an OBGX operation is violated. A fault is not an ordinary recoverable failure and is not part of the operation's normal return type.

When a fault triggers, the implementation must:

- NOT return to the caller of the operation;
- NOT terminate itself or the host process;
- NOT terminate or corrupt packs that did not participate in the faulting operation.
- Redirect the execution flow of the caller pack to another location, often a fault handler.

OBGX does not specify how a language binding implements a fault. A binding may map it to a trap, exception, virtual-machine error, host-side error propagation, or another mechanism appropriate to that binding. This does not define a uniform OBGX exception system.

Recoverable failures that are part of an interface's normal operation may continue to be represented by success or result data defined by that interface.

A complete list of specified possible causes of fault is listed below. A binding may define additional causes of faults.

### 1. Out-of-Bounds Access

Access to an array or vector with an index outside that container's valid index domain produces an out-of-bounds fault.

An out-of-bounds access produces neither a default value nor an undefined value. The index MUST NOT be wrapped or clamped, and the fault does not require the element type to have a default value. It MUST NOT be represented as an ordinary recoverable-failure return value.
